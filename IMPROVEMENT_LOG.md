## Completed

- **#1 Payment status endpoint locked down** — `GET /api/pay/:orderId` previously had no auth; anyone with an order id could read payment details and trigger gateway syncs. Now requires a stakeholder role (paying customer via `Payment.customerID`, involved salon via `Payment.salonId`, or admin), enforced in route middleware + `canAccessPayment` controller check that runs *before* any Cashfree call. 7 new tests (`tests/payment-status-auth.test.js`). Tests: 21 → 28.

- **#2 Auth & input hardening** — admin login now uses `crypto.timingSafeEqual` over SHA-256 hashes (no timing leak, both fields always compared); signup endpoints (`/api/user/signup`, `/api/business/signup`, legacy `/api/buisness/signup`) now share the strict login rate limiter; public `getAllActiveServicesBySalonId` validates `salonId` with a zod query schema.

- **#3 Pagination for appointment listings** — added shared `paginateQuery`/`buildMeta` helpers (`utils/pagination.js`: page/limit coerced + clamped to 1..50, defaults 1/10) and applied them to customer `/api/appointment/getAll`, salon `/sceduledAppointments`, and admin `/appointments/getall` via `findAndCountAll`. Fully backward compatible: no `page`/`limit` params → legacy bare array (existing React + legacy JS consumers untouched); either param present → `{ data, page, limit, total, totalPages }` envelope. 15 new tests in `tests/pagination.test.js` cover clamping, both response shapes, meta math, and scoping. Tests: 28 → 43.

- **#4 Password reset flow** — customers can self-service forgotten passwords: `POST /api/user/forgot-password` issues a random 256-bit token of which only the SHA-256 hash plus a 60-minute expiry are stored (the plaintext link is emailed via a new `sendPasswordResetEmail` helper in the Brevo service, which stays a safe no-op when unconfigured), and `POST /api/user/reset-password` verifies token + email against the hash and window, rotates the bcrypt password (cost 10), and clears both token fields; both endpoints respond identically whether or not the account exists (no enumeration). They're public but share the strict login rate limiter — extracted to `middlewares/rateLimiters.js` so app.js mounts and route-level guards use one policy — with new zod schemas (`forgotPasswordSchema`, `resetPasswordSchema`, newPassword min 8). Because `sync()` never ALTERs existing tables, the two nullable user columns are backfilled at boot by a reusable `utils/ensureColumns.js` helper. 7 new tests in `tests/password-reset.test.js`. Tests: 43 → 50.

- **#5 In-app notifications** — a `notifications` table (`recipientRole` customer|salon, plain integer `recipientId` refs — no FK associations, so no circular-import risk) plus a fire-and-forget `notify()` service (`services/notificationService.js`) that catches and logs every failure so it can never break an already-successful booking flow. Hooks are wired after each DB write succeeds: booking finalized → salon gets "New booking" (`services/paymentService.js`, which is where bookings actually materialize from successful payments); status transitions confirmed/declined/completed → customer; customer cancellation → the other party (the salon). Three new endpoints at `/api/notifications` — list (newest-first, same backward-compatible legacy-array/envelope pagination contract as the appointment listings), mark-one-read (404s foreign/unknown ids), and read-all — scoped via `authMiddleware.requireRole('customer','salon','admin')` with customers keyed on `req.user.userId` and salons on `req.user.salonId`. 12 new tests in `tests/notifications.test.js`. Tests: 50 → 62.

- **#6 Reschedule appointment** — customers can move their own upcoming booking via `PATCH /api/appointment/:appointmentId/reschedule`: a pure `canReschedule(appointment, now)` rule (`utils/statusRules.js`) reuses the cancellation semantics (status pending|confirmed only, start strictly >24h away), ownership is enforced like cancel, and an optional `staffId` may reassign to any staff of the same salon who provides the same service. The new slot is revalidated against salon working hours and conflict-checked via `conflictingStaffIds` (blockouts + other bookings, now accepting an `excludeAppointmentId` so a booking can't collide with itself), returning 409 `New slot is not available` when busy; on success date/time/endTime/staff are persisted and the salon receives a fire-and-forget `booking.rescheduled` notification carrying old→new date/time. 7 new direct-controller tests in `tests/reschedule.test.js`. - **#46 Idempotency keys** — `models/idempotencyModel.js` + `utils/idempotency.js`. The problem: a client that times out on `POST /pay` can't know whether the first attempt succeeded, so a retry creates a SECOND Cashfree order and a second booking — the customer is charged twice. Now a client sends `Idempotency-Key` and retries replay the stored response instead of re-executing (Stripe-compatible protocol, so existing client libraries work). Three distinct 409s guard the dangerous cases: key reused with a *different* body (`IDEMPOTENCY_KEY_REUSED`), retry while the first is still in flight (`IDEMPOTENCY_IN_FLIGHT`, from the row reserved before the handler runs — which is what actually prevents the double charge), and a lost create race on the unique scope+key index. 5xx is never cached, and a store failure degrades to non-idempotent execution rather than erroring a healthy API. Keys are namespaced per principal (`role:id`) so two users picking the same uuid can't collide. 6 new tests. Tests: 426 → 432.

- **#47 Double-booking prevention** — `services/bookingGuard.js`. The booking flow already checked for conflicts before inserting, but check-then-insert is a TOCTOU race: two payments finalizing milliseconds apart can both pass the check and both insert, producing two charges for one chair. Two layers, because neither alone is enough. (1) A PARTIAL UNIQUE INDEX on `(staffId, date, time)` with `WHERE status NOT IN ('cancelled','declined','no-show')` — partial is essential, since a plain unique index would permanently burn any slot that was ever cancelled. (2) `createBookingSafely()`, now the path `services/paymentService.js` uses to materialize a booking, translates a database uniqueness violation into the same `SLOT_TAKEN` error the pre-check produces, so callers see one consistent failure instead of a 500. Index creation is best-effort at boot: MySQL/MariaDB are skipped (no partial index support) and a legacy database with pre-existing duplicates logs a loud warning and keeps serving rather than refusing to start — availability beats strictness for a salon already taking bookings. `findDuplicateSlots()` reports the offending rows so an operator can clean up and retry.

- **#48 Optimistic concurrency** — `utils/optimisticConcurrency.js` + a `version` column on `Appointments` (backfilled at boot `NOT NULL DEFAULT 0`, so every legacy row is legitimately version 0). Two actors editing one booking (salon confirms while the customer cancels) previously meant the second write silently won. Now reads expose `ETag: W/"<id>-<version>"` and a mutating request may send `If-Match`; a stale version gets **412 Precondition Failed**, a malformed header **400**, a header naming a different row **409**. Chosen over pessimistic row locking because booking edits are short, human-driven and rarely collide — and SQLite makes `SELECT ... FOR UPDATE` awkward. `bumpVersion` uses Sequelize's `increment()`, which emits `version = version + 1` and is therefore atomic in SQL with no read-modify-write race. No header means an unconditional write, so every existing client is unaffected.

- **#49 Money helpers** — `utils/money.js`: integer minor units everywhere, decimals only at the edges. The bug this exists to prevent is `0.1 + 0.2 === 0.30000000000000004`, and a float error that survives into a payment ledger is a reconciliation incident. `toMinor` parses decimal *strings* through an exact digit-shifting path (no float ever touches the value) with half-up rounding, so `'1.005'` → 101 — the case a naive `Math.round(1.005 * 100)` gets wrong. Handles zero-decimal (JPY) and three-decimal (BHD) currencies and grouping separators, and returns `null` for garbage instead of `NaN`. `allocate()` splits an amount across ratios without losing or inventing a single paisa: the remainder is distributed to the largest fractional parts, so `allocate(1000, [1,1,1])` sums to exactly 1000 where naive division gives 999. Plus `discountFor` (capped, never exceeding the price), `format` via `Intl`, and `formatCompact` using lakh/crore.

- **#50 Salon-local timezone helpers** — `utils/timezone.js`. The app stores bookings as a DATEONLY date plus a TIME — deliberately wall-clock, since "3pm Saturday" means 3pm on the *salon's* clock — so every comparison against "now" has to ask *now where?*. A UTC server deciding "today" for an Asia/Kolkata salon rolls over at the wrong moment, and `/staff/today` shows tomorrow's list for five and a half hours. Everything is built on `Intl` (core, carries the real IANA database including DST rules). `zonedToUtc` solves the genuinely hard direction — there is no "the UTC offset of a timezone", the offset depends on the date — by probing: guess an instant, ask Intl what wall time that shows, measure the error against a *frozen* target, and correct. Two iterations converge; DST "spring forward" gaps resolve forward, matching how a wall clock actually behaves. Also `generateSlots` (respecting the salon's step and never offering a slot whose duration would run past closing), `overlaps` with half-open intervals, and calendar-safe `addDays`/`daysBetween`. **Bug found by the tests:** the probe measured its error against the moving guess instead of the frozen target, so it subtracted the offset again on every pass and diverged (19:30 → 14:00 → 08:30 → 03:00) instead of converging.

- **#51 Service soft-delete** — deleting a service used to `destroy()` it unconditionally. - **#55 One-tap rebook** — `services/rebookService.js` + `POST /api/appointment/:id/rebook`. The most common booking in a salon app is the same booking as last time, so making the customer walk the whole flow again (find salon → pick service → pick staff → hunt a date) is friction on the highest-intent action in the product. It answers one question: given a booking you already made, when can you have it again? **It returns a checkout payload, not a booking** — every booking here is paid for through the gateway, so creating a "pending" appointment would either hold a chair for someone who never pays or create a booking with no money behind it. Only terminal/past sources are rebookable (`completed`, `cancelled`, `no-show`, `declined`); a live booking gets `409 NOT_REBOOKABLE`, because moving one is what reschedule (#6) is for and overlapping the two would let a customer rebook their way out of the 24-hour cancellation rule. The search scans forward day by day and the first day with *any* free slot wins; `preferSameTime` then sorts by distance from the ORIGINAL time of day (someone who books a 6pm cut after work wants another 6pm cut, not the 9am opening slot that happens to be free first) — free-ness is decided independently and always wins. Cheap checks run first: salon hours and lead time are pure functions of the salon row and cost zero queries, so a closed day never reaches the conflict scan, and `conflictingStaffIds` runs once per candidate slot rather than once per stylist. If the original stylist is busy or blocked out, it falls through to a free colleague and reports `sameStaff: false` — "rebooked with Priya" is a different promise from "rebooked". Archived services (#51) are refused. **Bug found by the tests:** a slot earlier today is technically *free*, so a salon with no lead time would happily offer 09:00 at 5pm; lead time cannot catch this, because a null lead time means "bookable immediately" — about the future, not about retroactive bookings — so day zero skips any slot at or before now. **The same bug was hiding one layer down:** the first version derived "today" from `now.toISOString().slice(0, 10)` (the UTC day) while comparing against `now.getHours()` (the local hour) — on any host west of UTC in the evening those name two different days, so the search offered 09:00 "today" at 01:47 local. `utils/timezone.js` therefore gained `localDay`/`localTime`: the host's clock is the system's frame of record, because `validateLeadTime` rehydrates `${date}T${time}` as host-local time, and even on a UTC server like Render `todayIn()` and `localDay()` disagree for five and a half hours a day. `horizonDays` is *clamped* to 1..60 rather than rejected: asking for a 500-day search should search 60, not 400, and the cap keeps the scan bounded since every day costs a query. `recentDistinctBookings` backs the "book again" rail with a bounded 200-row scan deduped on `salon|service|staff` in JS (dialect-portable, no `DISTINCT ON`).

- **#56 Price quote** — `services/quoteService.js` + `POST /api/appointment/quote`. Before this the checkout panel could only show the service price and the real total (promo, tip, group size) appeared for the first time at the gateway — the worst possible moment to learn a booking costs more than you thought. **The rule this module exists to enforce: the quote and the charge are computed by the same code.** A second, parallel implementation of discount math would drift from the real one within a sprint, and a quote that disagrees with the charge is worse than no quote at all, because it's a promise the app breaks. So the price comes from `getAuthoritativePrice` and the discount from `resolvePromo` — the exact functions `/pay` uses — which also means a client can't post its own number and talk us into a cheaper quote. Amounts are integer minor units throughout (#49), with `Intl`-formatted strings alongside so no client ever re-derives them. The tip rides **on top of** the discounted price, matching the payment path: a tip rewards the service actually received, not a percentage of list price. The total is clamped at zero — a promo worth more than the service is the salon's pricing mistake, and charging a negative amount would be far worse than absorbing the difference. An invalid promo is a `400`, never silently dropped: the customer has to learn now, not at the gateway. Group quotes include a `perPersonAmount` built with `money.allocate`, so the per-head figures sum back to the total exactly. **Sharp edge documented in the code:** `getAuthoritativePrice` takes `(serviceId, salonId)` — ids, not rows — and returns a tagged union (`{price}` | `{mismatch}` | `null`); passing the already-loaded Sequelize instance (the obvious thing to do, since the row is right there) is rejected outright.

- **#57 Booking history filters** — `GET /api/appointment/getAll?status=&from=&to=&salonId`. A customer with two years of bookings couldn't find last March's haircut without paging through all of it. - **#58 Recently viewed salons** — `models/recentlyViewModel.js` + `services/recentViewsService.js`. Browse history is the cheapest convenience feature in a booking app and one of the most used ("where was that place I looked at yesterday?"), and it's also easy to get wrong in a way that quietly becomes a liability: a table that grows forever, and a read path that 500s the moment an admin deletes a salon out from under it. Three deliberate decisions: a repeat view **updates** the existing row instead of inserting another, so the list is a recency ranking rather than a wall of duplicates; the table is pruned to the newest 20 per user on every write, which is bounded storage with no cron job — and the prune is a two-step select-ids-then-delete because SQLite can't be trusted with `ORDER BY` inside `DELETE ... WHERE id IN` across dialects; and reads hydrate salons **by hand** and skip rows whose salon no longer exists, so a dangling reference degrades to "not shown" rather than a failed dashboard request. Recording a view is fire-and-forget — a failed write logs a warning and returns `null`, because browse history must never break the page load that triggered it. The model deliberately declares no FK association, so nothing cascades: `deleteMyAccount` clears it explicitly, and a test asserts that, since "the GDPR path forgot a table" is invisible until it's a compliance incident.

- **#59 Favorite staff** — `models/favoriteStaffModel.js`. Customers are loyal to a person, not a building, and until now the app could only remember the building. Each row stores the salon/service context the stylist was chosen in, so "Priya · Orchid Spa" renders in one call. - **#60 Cancellation reasons** — an optional reason from a fixed vocabulary plus a ≤200-char note, recorded on cancellation, and `GET /api/salonsdashboard/analytics/cancellation-reasons`. A cancellation **count** tells a salon something is wrong; the **reason** tells them what. "12 cancellations" is a bad month, but "9 of them were schedule conflicts at 6pm" is a staffing decision while "9 were too expensive" is a pricing one — opposite responses, and without the breakdown a salon will guess, usually wrong. The response includes the cancellation *rate* because the raw count is meaningless alone: 12 out of 400 visits is a good month, 12 out of 30 is an emergency. Only customer cancellations carry a reason, so pre-#60 rows and salon-side cancellations land in an explicit `unspecified` bucket that is **reported, not hidden** — a large unspecified bucket is itself a signal, and it shrinks over time as more customers pick a reason. The reason is deliberately *not* put in the cancellation notification: the salon sees the aggregate rather than a raw complaint against an individual customer. The field stays optional so the existing SPA's cancel button keeps working byte-identically. **Bug found by the tests:** reading `req.body.reason` unguarded turned "cancel without a reason" — the common case, and one this handler also hits when called directly by tests and internal callers with no body at all — into a 500 on a path that used to work, which is exactly the regression an optional field must never cause. It now destructures with defaults from `req.body || {}`.

- **#61 Recurring booking series** — `models/recurringSeriesModel.js` + `services/recurringService.js` + a daily sweep in `app.js`. A customer who gets a haircut every six weeks shouldn't re-enter the same booking eight times a year. Three decisions carry the design. **Occurrences are materialized late (14-day horizon), not up front**: creating all N at series-creation time would commit a price, a stylist and a chair that may not exist six months from now, and would hold inventory for visits the customer may yet cancel. **Occurrences are created `pending`**: every booking here is paid through the gateway, so a series is a standing *request*, not a purchased right to a chair — charging someone on a timer, with nothing pressed, would be indefensible; the salon confirms each visit and collects in person, exactly like any other pending booking. **Idempotency comes from counting durable rows** ("how many occurrences are due, how many exist?") rather than advancing a mutable next-date cursor — a cursor is lost work on a crash and double-advance on a replay. A partial unique index on `(seriesId, occurrenceIndex) WHERE seriesId IS NOT NULL` backs it (partial so one-off bookings, which all have a NULL `seriesId`, stay out of the index entirely), and a concurrent sweep winning the race counts as *skipped*, not failed. An occurrence that clashes or falls outside working hours is skipped rather than double-booked — one bad visit must never stop the whole sweep or cancel the customer's series — and the counter is advanced to what actually materialized so a skipped occurrence is retried next time instead of being burned. "Monthly" is 30 days, not a calendar-month step: a calendar month isn't a fixed length and "the 31st of every month" is a bug waiting to happen. Cancelling is terminal and leaves existing appointments alone (those are real bookings with their own cancellation rules; silently deleting them would strand both sides), and the GDPR path cancels any active series so the sweep stops booking for a deleted account — otherwise it would materialize appointments forever, because nothing else would ever stop it.
